# Safety audit: generated TOSA FlatBuffers bindings

The public and project-authored portions of `virtio-accel-tosa` use `#![deny(unsafe_code)]`.
`src/generated.rs` is the only local exception. It was generated by `flatc 25.2.10 --rust` from the
checked-in TOSA Tools `v2026.05.0` schema and is compiled as a private module with a local
`#[allow(unsafe_code)]`.

## Why an exception exists

Official FlatBuffers Rust bindings implement `Follow` and `Push` with unsafe methods and use
unchecked table-slot access after verification. Rewriting those generated accessors would create a
fork of the serialization ABI and a larger, less reviewable parser. The safe FlatBuffers verifier
is therefore the trust boundary; no generated unchecked-root function is called.

The exception does not reach downstream callers:

- the generated module is private;
- no generated table, union, builder, `Table`, `Follow`, or unchecked accessor appears in the
  public API;
- `parse` first checks the `TOSA` identifier and calls `root_as_tosa_graph_with_opts` with finite
  depth, table-count, and apparent-size ceilings;
- public views can only be constructed from the verified root and contain no unsafe methods; and
- the second validation pass bounds collections and constants before any `Model` is returned.

## Audited generated invariants

Generated `Follow` implementations construct a FlatBuffers table at a location selected by the
runtime verifier. Generated scalar and table accessors rely on that table having a valid vtable,
field offsets, alignment, vector bounds, UTF-8 strings, and union payload. Generated union accessors
are not used by project-authored code; the verifier still checks that each serialized union payload
matches its attribute discriminant.

The writer-side `Push` and builder implementations are compiled because `flatc` emits readers and
writers together. They are private and are used only by same-crate tests to construct fixtures.
Production parsing never invokes them.

## Regeneration and review

Regeneration is a security-sensitive source change. Reviewers must:

1. verify `schema/tosa.fbs` against the recorded upstream release and SHA-256;
2. use the recorded `flatc` version, with no local schema edits;
3. inspect changes to `Follow`, table access, root verification, union verification, and identifier
   handling;
4. confirm the generated module remains private and the unchecked-root functions remain unused;
5. update the stable TOSA operator/data-type cutoffs if and only if the accepted specification
   boundary intentionally changes; and
6. run malformed-input, resource-limit, portable-target, MSRV, Clippy, docs, and package tests.

Unsafe code in the external FlatBuffers runtime is governed by that dependency's own audit and the
workspace dependency policy; this document covers only unsafe code compiled from this crate.
