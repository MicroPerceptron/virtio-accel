# virtio-accel.org website

This module builds and deploys the public site for `virtio-accel.org`. It is
deliberately **not** a Cargo workspace member: it is a Python + mdBook project,
so it stays out of `cargo fmt --all`, `cargo clippy --workspace`, and
`cargo doc --workspace` and never affects the crate release pipeline.

## Layout

| Path | Purpose |
| --- | --- |
| `book.toml` | mdBook configuration (pinned to mdBook 0.5.x) |
| `build.py` | Single build entry point: curates docs, rewrites links, generates `SUMMARY.md`, builds rustdoc + mdBook, overlays the landing page |
| `check.py` | Validates the built tree: required pages, the landing overlay, dangling links, `CNAME` |
| `content/index.html` | The landing page &mdash; a standalone document, not an mdBook chapter |
| `content/api.md` | The API reference index chapter |
| `theme/` | Favicon, docs-reader stylesheet, sidebar brand script |
| `src/` | Generated by `build.py`; git-ignored |
| `book/` | Generated site output; git-ignored |

## The three layers of the site

The site is three separately-generated things stitched into one tree:

1. **`/` &mdash; the landing page.** `content/index.html` is a hand-written,
   self-contained HTML document (its CSS is inlined). `build.py` copies it over
   `book/index.html` *after* `mdbook build`, replacing the copy mdBook emits for
   the book's first chapter. That chapter is also written under its own name
   (`getting-started.html`), so nothing is lost. Keeping the landing page out of
   mdBook is what lets it have a layout the book's chrome cannot express.
2. **`/docs/`, `/getting-started`, `/api` &mdash; the docs reader.** Stock
   mdBook, restyled by `theme/css/custom.css`. mdBook picks a built-in theme by
   class on `<html>`, so rather than fork `index.hbs` the stylesheet rebinds two
   of them: `.navy` becomes the dark palette the landing page uses (and is the
   default), `.light` becomes a matching light companion. The reader can still
   switch between them from the theme menu.
3. **`/api/` &mdash; rustdoc.** `cargo doc --workspace --all-features --no-deps`,
   copied under `book/api/` with a generated top-level index, because
   `cargo doc --workspace` does not emit one.

Design tokens are duplicated in two places by necessity &mdash; the inline
`<style>` in `content/index.html` and the palette block in
`theme/css/custom.css`. **Change both together.**

## Local build

Requires Rust (1.85+) and mdBook 0.5.x:

```sh
cargo install mdbook --version 0.5.4 --locked
python3 website/build.py
python3 website/check.py
```

The finished site is in `website/book/`. Serve it locally with any static file
server:

```sh
python3 -m http.server -d website/book 8000
```

`build.py` accepts `--skip-rustdoc` and `--skip-mdbook` to iterate on one half
of the pipeline. `check.py` notices when `book/api/` is absent and skips links
into the rustdoc tree rather than reporting them as dangling, so
`build.py --skip-rustdoc` followed by `check.py` is a valid fast loop.

## What gets published

- The curated narrative docs under `docs/` (specification, wire ABI, virtqueue,
  architecture, threat model, portability, performance, public API, release
  policy, backend guide, Hexagon matrix, and the 1.0 release notes).
- The repository `README.md` as "Getting started".
- rustdoc for the whole workspace under `/api/`.

The internal `docs/agents/` and `docs/plans/` trees are **excluded**. Links from
curated docs to repository files that are not part of the site (source files,
`include/virtio_accel.h`, conformance artifacts, licenses) are rewritten to
point at GitHub.

Adding a page means adding it to `CURATED` **and** to `write_summary()` in
`build.py`; `check.py`'s `REQUIRED_PAGES` is the backstop that fails the build
if the two drift apart.

## CI/CD

`.github/workflows/website.yml` has three jobs.

`check-site` runs on **every pull request** that touches `docs/**`,
`website/**`, `README.md`, `crates/**`, or the manifests. It builds exactly what
a push to `main` would publish and then runs `check.py`, so a doc edit that
breaks a cross-link, deletes a page something still points at, or fails rustdoc
fails the PR rather than reaching the live site. It uploads nothing, configures
no Pages state, and holds no permission beyond `contents: read`.

`build-site` and `deploy-pages` run on pushes to `main` and after a successful
`Publish crates` run (via `workflow_run`), so a release refreshes the rustdoc
automatically. The build job runs `build.py`, runs `check.py`, and uploads
`website/book/` as a Pages artifact; the deploy job publishes it. `build.py`
writes a `CNAME` file into the built tree so the `virtio-accel.org` custom
domain is pinned to the artifact itself.

No secrets, servers, or SSH keys are required: deployment uses the workflow's
own OIDC token (`id-token: write`) and Pages permission (`pages: write`), both
scoped to the `deploy` job.

Because the site is generated from `docs/` and `README.md` on every run, a
merged documentation PR republishes the docs with no separate step.

## One-time GitHub Pages setup

1. **Settings → Pages → Build and deployment → Source:** select
   **GitHub Actions**.
2. **Settings → Pages → Custom domain:** enter `virtio-accel.org`. This is
   already a verified organizational domain, so GitHub will validate it
   immediately. The workflow also emits a matching `CNAME`, so the two agree.
3. Tick **Enforce HTTPS** once the certificate is provisioned (usually a few
   minutes after the domain check passes).
