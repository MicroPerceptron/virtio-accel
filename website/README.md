# virtio-accel.org website

This module builds and deploys the public site for `virtio-accel.org`. It is
deliberately **not** a Cargo workspace member: it is a Python + mdBook + Sphinx project,
so it stays out of `cargo fmt --all`, `cargo clippy --workspace`, and
`cargo doc --workspace` and never affects the crate release pipeline.

## Layout

| Path | Purpose |
| --- | --- |
| `book.toml` | mdBook configuration (pinned to mdBook 0.5.x) |
| `build.py` | Single build entry point: curates docs, rewrites links, generates `SUMMARY.md`, builds rustdoc + mdBook, overlays the landing page |
| `python/` | Sphinx configuration and public module directives; signatures and prose come from Python docstrings |
| `requirements.txt` | Pinned documentation dependencies |
| `release_trigger.py` | Require an actual production upload before a release-triggered refresh |
| `check.py` | Validates the built tree: required pages, the landing overlay, dangling links |
| `tls_check.py` | Fails when the certificate the live site serves does not verify or is not being renewed |
| `content/index.html` | The landing page &mdash; a standalone document, not an mdBook chapter |
| `content/api.md` | The API reference index chapter |
| `theme/` | Favicon, docs-reader stylesheet, sidebar brand script |
| `src/` | Generated by `build.py`; git-ignored |
| `book/` | Generated site output; git-ignored |

## The layers of the site

The site is four separately-generated things stitched into one tree:

1. **`/` &mdash; the landing page.** `content/index.html` is a hand-written,
   self-contained HTML document (its CSS is inlined). `build.py` copies it over
   `book/index.html` *after* `mdbook build`, replacing the copy mdBook emits for
   the book's first chapter. That chapter is also written under its own name
   (`getting-started.html`), so nothing is lost. Keeping the landing page out of
   mdBook is what lets it have a layout the book's chrome cannot express.
2. **`/docs/`, `/getting-started`, `/api` &mdash; the docs reader.** Stock
   mdBook, restyled by `theme/css/custom.css`. mdBook picks a built-in theme by
   class on `<html>`, so rather than fork `index.hbs` the stylesheet rebinds two
   of them: `.navy` becomes the dark palette the landing page uses (and is the
   default), `.light` becomes a matching light companion. The reader can still
   switch between them from the theme menu.
3. **`/api/` &mdash; rustdoc.** `cargo doc --workspace --all-features --no-deps`,
   copied under `book/api/` with a generated top-level index, because
   `cargo doc --workspace` does not emit one.

4. **`/python/api/` — Sphinx.** Autodoc imports the two public modules directly
   from `python/`, follows `__all__`, and renders their signatures, docstrings,
   methods and properties. It does not import `_native` or probe hardware, so
   neither a Rust extension build nor any vendor SDK is needed. Warnings fail
   the build. The reference includes search, an object inventory and an executable
   CPU-reference example. The guide at `/python/` is curated from `python/README.md`.
   The reference labels the SDK version from `pyproject.toml` and explicitly
   follows current `main`, which may contain unreleased changes.

Design tokens are duplicated in two places by necessity &mdash; the inline
`<style>` in `content/index.html` and the palette block in
`theme/css/custom.css`. **Change both together.**

## Local build

Requires Rust (1.85+), Python 3.14 and mdBook 0.5.x:

```sh
python3.14 -m venv .venv-docs
. .venv-docs/bin/activate
python -m pip install --only-binary=:all: -r website/requirements.txt
cargo install mdbook --version 0.5.4 --locked
python3 website/build.py
python3 website/check.py
```

The finished site is in `website/book/`. Serve it locally with any static file
server:

```sh
python3 -m http.server -d website/book 8000
```

`build.py` accepts `--skip-rustdoc` and `--skip-mdbook` to iterate on one half
of the pipeline. `check.py` notices when `book/api/` is absent and skips links
into the rustdoc tree rather than reporting them as dangling, so
`build.py --skip-rustdoc` followed by `check.py` is a valid fast loop.

## What gets published

- The curated narrative docs under `docs/` (specification, wire ABI, virtqueue,
  architecture, threat model, portability, device support, performance, public
  API, release policy, backend guide, Hexagon matrix, and the 1.0 release notes).
- The repository `README.md` as "Getting started".
- rustdoc for the whole workspace under `/api/`.
- The Python guide under `/python/` and generated Python API under `/python/api/`.

The internal `docs/agents/` and `docs/plans/` trees are **excluded**. Links from
curated docs to repository files that are not part of the site (source files,
`include/virtio_accel.h`, conformance artifacts, licenses) are rewritten to
point at GitHub.

Adding a page means adding it to `CURATED` **and** to `write_summary()` in
`build.py`; `check.py`'s `REQUIRED_PAGES` is the backstop that fails the build
if the two drift apart.

## CI/CD

`.github/workflows/website.yml` validates PRs and gates production refreshes before building and deploying.

`check-site` runs on **every pull request** that touches `docs/**`,
`website/**`, `python/**`, `README.md`, Rust sources, assets, release workflows,
or the Rust/Python manifests. It builds exactly what
a push to `main` would publish and then runs `check.py`, so a doc edit that
breaks a cross-link, deletes a page something still points at, or fails rustdoc
fails the PR rather than reaching the live site. It uploads nothing, deploys
nothing, and holds no permission beyond `contents: read`.

`build-site` runs on pushes to `main`, after an actual production upload from `Publish crates` or `Release Python SDK`
(via `workflow_run`), and on manual dispatch. The refresh gate checks jobs from the
exact upstream attempt: failed, cancelled and skipped uploads, build-only Python
runs and TestPyPI uploads do not deploy. A Python tag also skips the Rust publisher;
that skipped Rust job does not cause a duplicate refresh.

Production builds always check out current `main`, including manual and release
refreshes. An older release therefore cannot roll documentation back to its tag.
The gate has read-only Actions access and never executes an upstream artifact or
checks out a triggering branch. The `production` environment still gates deployment. It builds, checks, and uploads `website/book/` as a workflow
artifact.

`deploy-droplet` downloads that artifact and `rsync`s it to the droplet over
SSH. It runs in the `production` environment, so the deploy can be gated behind
required reviewers if you want that. The site is static, so **nothing is built
on the droplet** -- it needs `nginx` and `rsync`, and no Rust, mdBook, Python,
or Docker.

`verify-live-site` runs after the sync, as a separate job that holds no deploy
secret and is outside the `production` environment. It runs `tls_check.py`
against `virtio-accel.org` and **fails the run when the served certificate does
not verify** (expired, wrong hostname, untrusted issuer): that is not transient,
and it puts the whole site behind a browser security error even though the
files synced. A non-200 response, an unreachable host, or low remaining
validity only warns there.

`.github/workflows/website-tls.yml` (`Website TLS`) is the certificate monitor.
It runs `tls_check.py` daily and on manual dispatch, and fails long before
expiry; see [TLS certificate](#tls-certificate).

To validate locally, run `python -m unittest discover -s website -p 'test_*.py' -v`,
then build and run `check.py`. In addition to links and required pages, the checker
requires every public Python export and public method/property to appear in the API
reference with a docstring. Add documentation alongside new API code; no duplicate
hand-maintained function list is needed. Sphinx doctests run as part of `build.py`.

Because the site is generated from `docs/` and `README.md` on every run, a
merged documentation PR republishes the docs with no separate step.

### Required repository configuration

Set these under **Settings -> Secrets and variables -> Actions**, either
repository-wide or on the `production` environment. The deploy job checks all
four up front and fails with a list of what is missing, rather than half-running.

| Secret | Purpose |
| --- | --- |
| `DEPLOY_SSH_HOST` | Droplet IP address or hostname |
| `DEPLOY_SSH_USERNAME` | SSH login user, e.g. `deploy` |
| `DEPLOY_SSH_SECRET` | Private key PEM for that user, no passphrase (include the `-----BEGIN…-----` / `-----END…-----` lines) |
| `DEPLOY_PATH` | Absolute web root on the droplet, e.g. `/var/www/virtio-accel.org` |

Optional:

| Name | Default | Purpose |
| --- | --- | --- |
| `DEPLOY_SSH_PORT` | `22` | SSH port |
| `DEPLOY_SSH_KNOWN_HOSTS` | *(unset)* | Pinned host key. Without it the workflow trusts the droplet's key on first sight and logs a warning. Get the value with `ssh-keyscan -p <port> <host>`. |

`DEPLOY_PATH` and `DEPLOY_SSH_PORT` may be repository **variables** instead of
secrets; the workflow accepts either.

`DEPLOY_PATH` deliberately has **no default**. An earlier version of this
workflow hardcoded one, which is how a deploy can quietly land in a directory
nothing serves.

## Droplet setup

The droplet serves the synced tree with nginx. It needs `nginx` and `rsync`
installed, a deploy user that owns the web root, and that user's public key in
its `authorized_keys`. Nothing else: no Rust, mdBook, Python, or Docker.

```sh
# As root.
apt-get update && apt-get install -y nginx rsync

# A deploy user that owns the web root and nothing else.
adduser --disabled-password --gecos "" deploy
install -d -o deploy -g deploy -m 755 /var/www/virtio-accel.org

# The public half of the key stored as DEPLOY_SSH_SECRET.
install -d -o deploy -g deploy -m 700 /home/deploy/.ssh
printf '%s\n' 'ssh-ed25519 AAAA... deploy@virtio-accel' \
  >> /home/deploy/.ssh/authorized_keys
chown deploy:deploy /home/deploy/.ssh/authorized_keys
chmod 600 /home/deploy/.ssh/authorized_keys
```

The deploy pins modes itself (`--chmod=D755,F644`), so nginx can always read
the tree no matter what the CI artifact round-trip did to permissions.

### What the nginx server block must do

`root` points at `DEPLOY_PATH`, and mdBook's hashed assets can be cached hard
because their names change whenever their contents do:

```nginx
root /var/www/virtio-accel.org;
index index.html;

location / {
    try_files $uri $uri/ =404;
}

# Content-addressed assets mdBook emits with a hash in the filename.
location ~* -[0-9a-f]{8}\.(css|js|svg)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}

error_page 404 /404.html;
```

Leave TLS to certbot (`certbot --nginx -d virtio-accel.org`); it writes and
renews the `listen 443 ssl`, `ssl_certificate`, and HTTP-to-HTTPS redirect lines
in the same server block. Edit `root` in place rather than replacing the file,
or those lines are lost. `nginx -t && systemctl reload nginx` after any change.

The deploy `rsync`s with `--delete`, so the served tree exactly mirrors the
build and a page removed from `SUMMARY.md` stops being served. `.well-known` is
excluded so it cannot race certbot's ACME challenges.

### TLS certificate

certbot on the droplet obtains the certificate and is the only thing that can
renew it. Nothing in this repository takes part in renewal; the repository's
job is to notice when it stops.

**Renewal on the droplet.** The certbot package installs a systemd timer that
runs `certbot renew` twice a day, and that timer must be enabled and active:
`certbot.timer` when certbot came from `apt`, `snap.certbot.renew.timer` when it
came from `snap`. `certbot renew` is a no-op until a certificate is due
(30 days before expiry up to certbot 3.x, a third of the lifetime from 4.0 on,
which is also 30 days for a 90-day certificate). Because the certificate was
installed with `--nginx`, a successful renewal reloads nginx on its own.
Renewal uses the HTTP-01 challenge, so port 80 must stay reachable from the
internet and the HTTP server block certbot manages must stay in place.

Check all of it after building or changing the droplet, as root:

```sh
systemctl list-timers --all | grep -i certbot   # a timer exists and has a next run
systemctl is-enabled certbot.timer              # or snap.certbot.renew.timer
systemctl is-active certbot.timer               # or snap.certbot.renew.timer
certbot certificates                            # names covered and days left
certbot renew --dry-run                         # full renewal against the staging CA
```

`certbot renew --dry-run` must end with "all simulated renewals succeeded". It
exercises the challenge, the nginx plugin, and the firewall without touching
the live certificate, so it is the one command that shows whether the next
real renewal will work.

**The monitor.** `Website TLS` connects to `virtio-accel.org:443` every day
at 05:23 UTC, verifies the chain and the hostname against the runner's trust
store, and reads `notAfter` from the certificate the server presents. It checks
what is *served*, so a certificate that renewed on disk while nginx kept the old
one loaded is caught too. `tls_check.py` reports one of four outcomes per host:

| Outcome | Meaning | `Website TLS` | `verify-live-site` |
| --- | --- | --- | --- |
| `ok` | Verifies, and clears the threshold | pass | pass |
| `expiring` | Verifies, but under the threshold: renewal has stopped | **fail** | warn |
| `invalid` | Chain or hostname does not verify (includes expired) | **fail** | **fail** |
| `unreachable` | No TLS handshake after three attempts | **fail** | warn |

The threshold is 21 days, capped at a quarter of the certificate's own
lifetime. With today's 90-day certificates that is 21 days: renewal should have
happened at 30, so the monitor fails after about nine days of failed renewals
and three weeks before visitors are affected. The cap exists because Let's
Encrypt lifetimes drop to 64 days on 2027-02-10 and to 45 days on 2028-02-16;
a fixed 21 days would then fire during healthy operation, while a quarter of
the lifetime (16 and about 11 days) stays below certbot's renewal point.

GitHub notifies one person about a failed scheduled run: whoever created
`website-tls.yml`, or whoever last changed its `cron` line. That person must
have Actions notifications on; everyone else sees the red run on the Actions
tab. GitHub also disables scheduled workflows in a public repository that has
had no activity for 60 days, and a disabled monitor is silent. The workflow
holds only `contents: read`, so it cannot open an issue itself.

**When it fails.** On the droplet, as root:

```sh
systemctl status certbot.timer certbot.service   # snap: snap.certbot.renew.*
tail -n 100 /var/log/letsencrypt/letsencrypt.log
certbot renew --dry-run                          # reproduce the failure safely
certbot renew                                    # renew for real once it passes
systemctl enable --now certbot.timer             # if the timer was missing or disabled
nginx -t && systemctl reload nginx               # only if nginx still serves the old one
```

Then run `Website TLS` from the Actions tab (**Run workflow**) to confirm, or
locally: `python3 website/tls_check.py virtio-accel.org`.

The monitor covers the apex only, because that is the only name served. As of
2026-11-23 `www.virtio-accel.org` resolves to an address at the DNS host rather
than to the droplet, and no certificate covering `www` has ever been issued. If
`www` is brought into service as described under DNS below, add
`www.virtio-accel.org` to the `tls_check.py` command in both `website-tls.yml`
and `website.yml`.

### DNS

The apex points at the droplet's **reserved** IP, not its public IPv4, so the
droplet can be rebuilt or replaced without a DNS change:

| Type | Name | Value |
| --- | --- | --- |
| `A` | `@` | reserved IPv4 (`178.128.132.33`) |
| `AAAA` | `@` | droplet IPv6 |
| `CNAME` | `www` | `virtio-accel.org.` |

`DEPLOY_SSH_HOST` should be that same reserved IP for the same reason.

If `www` is served, it needs both the DNS record above and a certificate
covering it (`certbot --nginx -d virtio-accel.org -d www.virtio-accel.org`) --
a cert issued for the apex alone will fail the TLS handshake on `www`.
